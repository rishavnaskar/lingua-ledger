# Lingua Ledger - Devpost submission text

## Tagline (under 120 chars)
Multilingual document extraction where every field comes with a calibrated confidence score and a clear reason.

## Inspiration
Businesses receive invoices, receipts, forms, and contracts in many different languages. LLMs can extract data quickly, but nobody knows which fields to trust, so someone still has to double-check everything by hand. We wanted to build a tool that looks at each field and clearly tells you "auto-accept this" or "a human should look at this", and is actually right about how often it is right.

## What it does
- Takes a PDF or image in 7+ languages (we tested English, German, French, Spanish, Italian, Portuguese, Japanese, Indonesian, and Chinese).
- Automatically identifies the document type (invoice, receipt, form, contract) and language.
- Reads the file using two separate paths: a vision model looking directly at the page images, and Tesseract OCR paired with a text model. Both readers fill out the same strict schema.
- Reconciles both readers and runs rule-based validators (checking that line items add up to totals, dates parse and stay in order, IBAN checksums pass, VAT ids match official formats, currency codes are valid, and receipt change arithmetic works out).
- Combines reader agreement, OCR word confidence, validation results, and model self-confidence into a single raw score per field. Then it calibrates that score with isotonic regression so that a 0.9 actually means about 90 percent correct.
- Flags low-confidence fields for human review. The slider in our demo lets you see the live trade-off between human review workload and expected accuracy.
- Gives you visible proof for every extracted field: the exact bounding box on the page, plus which reader and validation rules backed it up.

## How we built it
We built the backend with Python 3.13 and FastAPI, and the frontend with Next.js 15. We used pydantic v2 schemas for strict data validation, along with Tesseract, pypdfium2, scikit-learn for calibration, and matplotlib for our report charts. For the LLM, we used Google Gemini (specifically gemini-3.5-flash-lite in the reported run, with an easy switch to Claude). We deployed the project to Vercel as two services (the web frontend and a containerised API) and wrote 225 unit tests. Every single number and chart in our slide deck and README is generated by running one command: `uv run ll eval report`.

## Results (198 public benchmark documents: synthetic multilingual invoices, CORD, SROIE, CUAD, FUNSD, XFUND)
- Field F1 (both readers + validators): synthetic invoices 98.6%, SROIE receipts 95.0%, CORD receipts 94.7%, CUAD contracts 60.2%, FUNSD forms 53.3%, XFUND forms 50.9% (strict pair matching, see challenges).
- Document type detected correctly 92.4%, language 88.9%.
- Calibration: expected calibration error 0.153 raw -> 0.022 calibrated on held-out fields; Brier 0.186 -> 0.148.
- Review routing: 74.9% of fields correct with no review; at threshold 0.85, 57.1% of fields go to a human and the rest are 94.4% correct; 63.9% reviewed gives 95%, 75.9% gives 98%.
- Cost: $0.91 for the whole run at list prices, $4.60 per 1,000 documents; about 2,435 input and 1,548 output tokens per document.
- Latency: reader p50 11.82 s, end-to-end p50 21.19 s including Free Tier rate limiting.

## Challenges we ran into
- Zero budget: We ran our entire evaluation on the Gemini Free Tier (which caps you at 15 requests/minute and 500/day on Flash-Lite). We had to build a custom rate limiter, 429 retries, and resumable evaluation runs, all while testing against Google's smallest model. These numbers are a floor, not a ceiling.
- Benchmark quirks: Form benchmarks like XFUND and FUNSD label raw text fragments rather than full fields, for example, a single address gets split into three separate key-value pairs. Our strict pairwise F1 scoring penalizes clean, merged output. We report the raw scores as is and explain why.
- Schema constraints: Gemini structured output does not support free-form dictionaries, so we had to format per-field confidence values as a list of {field, confidence} pairs.

## Accomplishments that we're proud of
- Calibration really works: Expected calibration error drops from 0.153 down to 0.022 on held-out test fields.
- A practical operating curve: Instead of giving you a single vanity accuracy number, we show that reviewing just 63.9% of fields gets you 95 percent accuracy on everything that gets accepted automatically.
- Very low cost: It runs at about $4.60 per 1,000 documents at standard list prices.
- A live interactive demo featuring real sample documents in seven languages.

## What we learned
Getting two independent readers to agree is our single strongest signal (93.8% correct when they agree vs 62.2% when they disagree). Whenever an arithmetic validation rule fails, it is almost always a real extraction error (only 14.0% correct). Calibrating on top of these concrete checks works far better than trusting the model's raw self-confidence.

## What's next
- Plugging larger reader models into the exact same pipeline (just change one environment variable).
- Better Japanese and Chinese form processing with layout-aware prompting and key normalisation.
- An active learning loop where human corrections continuously improve the calibrator.
- Bounding-box evidence for individual line items and direct CSV export for accounting software.
